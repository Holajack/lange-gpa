# Nuri (GPA) — Architecture & Sequencing: Phase 1–6 Build-Out

Project root: `/Volumes/LaCie/GPA_Language_Learning`. Synthesized 2026-07-18 from `phase1-completion-plan.md`, `phase2-blueprint.md`…`phase6-blueprint.md`, and `fidelity-review.md` (all in this directory). This document does not re-litigate content already in those five — it answers three questions they each answer locally but never together: what to build **once**, in what **order**, and **what ships next**.

---

## 1. Shared infrastructure to build once

Every one of the five blueprints independently proposes its own version of the same handful of systems. Read together, they collapse into **six concrete systems**, not five-to-eight per-phase bespoke builds. Building each once — generically, parameterized by phase — is cheaper than the sum of the per-phase versions and is what every blueprint's own §5 explicitly asks for ("build once, not per-phase" appears verbatim or in substance in all five).

### 1.1 Listening Library (recording archive + re-listen)
**What it is:** a Convex table + player UI for accumulating, taggable, re-listenable recordings, scoped to a grower (or a grower↔helper pair, or a topic/track). Core fields: `ownerGrowerId`, `helperId`, `kind` (primary/secondary/word/retell/journal-audio/etc.), `parentRecordingId` (for the primary→expansion nesting Phase 4 needs and the take-threading Phase 2's Clarify Player needs), audio ref, `durationSec`, `dateRecorded`, `relistenLog[]`, `consentState`, `erasureFlag`. UI needs: scrollable list, "tonight's queue" auto-populate, spaced-rotation resurfacing of older items, and a **shrinking-copy mode** (mark-as-familiar removes an entry from the next play-through without deleting the original — Phase 5's own delta note calls this "arguably the most app-able mechanic in the whole guide").
**Who needs it:** Phase 2 (light — 2–3h homework), Phase 3 (heavy — Bridge Story/Host Story re-listening), Phase 4 (life-story + expansion archive), Phase 5 (`p5-library` is literally named after this and has zero implementation today), Phase 6 (every discourse-track recording).
**Build cost vs. existing patterns:** new Convex table + storage refs (same shape as the existing `messages` voice-note storage), a player component that's a generalization of the session room's existing single-clip download. This is the single most-cited shared-infra item across all five blueprints — build it before or alongside Phase 2, not later.

### 1.2 Structured multi-take recording & massage primitive
**What it is:** the record → flag/annotate → clarify or re-record → thread-takes-together interaction shape. This single UI/state-machine pattern is independently proposed four times under four names: Phase 2's **Clarify Player** (§1.8), Phase 3's **Massage Player** (§1.1, segmented replay + "break it down / what does that mean / give an example" buttons), Phase 5's **`clarifyFlow.ts`** (a segment-based sibling to `sessionFlow.ts`, since Phase 5's unit of work is a timestamped audio segment, not a card), and Phase 6's **Massage Player reuse** for Stage-B and mass-media listening, plus Phase 4's deferred **Two-Recorder Technique**.
**Who needs it:** Phases 2, 3, 5, 6 directly; Phase 4 references it as future scope.
**Build cost vs. existing patterns:** a new state machine sibling to `sessionFlow.ts` (pure state-transition, countdown-owns-the-clock, same shape, different unit — segment instead of card), plus a shared player component with configurable prompt style and segment length per phase. Building this once with light per-phase configuration avoids four near-duplicate builds — explicitly flagged as such in Phase 3's own §5.

### 1.3 Word Log / cue-card cross-phase word-history store
**What it is:** a freeform, timestamped, source-linked word-history table (`word`, `gloss`, `sourceRecordingId`, `timestampSec`, `dateAdded`, `timesReviewed`) replacing/extending `vocab.ts`'s fixed 237-card deck and `profile.wordIds`. This is where the app's fixed-picture-deck data model structurally breaks — Phase 4's freeform personal vocabulary is the forcing function, but Phase 2 (word-sentence-word), Phase 3 (Word Log), and Phase 6 (10-words/hour remedial counter, Needs Analysis) all need the same primitive.
**Who needs it:** every phase 2–6, but it is **upstream of all of them** — it's also Phase 1's own foundational bug (M11 in the completion plan: `profile.wordIds` is populated by exactly one practice screen and the live session room never logs which cards were introduced at all). Every later phase's word-tracking feature would be built on undercounted data until this is fixed once, first.
**Build cost:** schema addition + fixing the one missing write-path in `session/page.tsx` that currently logs a numeric point count instead of card ids. Small in isolation; large in blast radius if skipped, since Phases 2–6 all silently inherit the bug.

### 1.4 Async relationship thread system (generalized `convex/messages.ts`)
**What it is:** extending the existing 1:1, sorted-clerk-id-pair-threaded `messages` table from `kind: "text"` (with `"voice"` schema-reserved but unbuilt) into a real generic attachment/subtype system: `sendVoiceMessage` (finish what the schema already reserves), a `"fact"` kind (Phase 2's daily ritual), `"journalEntry"` (Phase 4), `"topicNudge"` with `sourceExpansionId` (Phase 4, grounds nudges in something actually said — never a speculative new topic), a small **Idea Board** table (Phase 3, four shared lists), a **serialized Epic thread type** (introduced Phase 3, explicitly continues unmodified through Phase 6), and **topic-scoped threading** — extending the key from `{pair}` to `{pair, topicId}` so Phase 4 (per-storyteller), Phase 5 (per clarifying-session discourse context), and Phase 6 (per-discourse-track) threads don't collide.
**Who needs it:** every phase 2–6; each phase's blueprint independently says "this is not a new messaging system, it's phase-shaped structure on the existing one."
**Build cost:** mostly additive schema (`attachmentType`, `attachmentRef`, optional `topicId`) plus one new mutation per attachment kind, reusing the existing rate-limit/block-check plumbing `sendMessage` already has. Cheapest of the six systems relative to its reuse value.

### 1.5 Generalized helper (HelperProfile) matching & trust framework
**What it is:** replacing the single Phase-1-shaped `Nurturer` type and its one global `nurturerCertStatus` pass/fail with (a) a `helperRole: nurturer | mentor | community | expert` discriminant driving phase-appropriate marketplace views, (b) a **multi-module phase-certification framework** (module id, prerequisite chain, quiz bank per phase/sub-phase — Phase 2 needs 2A/2B/2C modules, Phase 3 a storyteller module, Phase 4 a confidentiality/ethics module, Phase 5 explicitly needs NO quiz-based cert at all since mentors are untrained by design), (c) **attribute-based search facets** beyond language+rate (`storytellingSample`, `walkOfLifeRoles`, `discourseSpecialties`, `mentorTraits.elaboratesWell`), and (d) a **post-session crowd-rating quality signal** that replaces one-time quizzes from Phase 4 onward, since "no training needed, communication is natural" is the guide's own stated model starting there.
**Who needs it:** Phase 2 (2A/2B/2C modules), Phase 3 (storyteller cert + `phasesGuided` actually used as a filter), Phase 4 (occupation facet, confidentiality ack instead of a quiz), Phase 5 (mentor-quality signal instead of `methodCertified`), Phase 6 (`discourseSpecialties` + eloquence rating + light expert-directory verification).
**Build cost:** the roster schema (`src/lib/nurturers.ts`) already has `phasesGuided` and `methodCertified` as unused-in-matching cosmetic fields — this is real filter-logic work plus a module-framework table, not a green-field data model. Also needs a "self-registered real contact" path (Phase 4/6 both want a grower to log a spouse/coworker/actual mechanic as a tracked relationship without going through marketplace booking).

### 1.6 Real credit/payment event pipeline
**What it is:** `convex/credits.ts`'s `recordEntry` currently throws by design ("Credits require a verified session or payment event"), plus a **new per-deliverable bounty payment shape** alongside the existing hourly `paidHours`/`exchangeHours` rails (Phase 5's recording-collection bounties, Phase 6's one-off expert-interview fees). Also gates: turning on `NEXT_PUBLIC_ENABLE_COMMUNITY_EXCHANGE` (default off today) for the `/world` + `requests.ts` + `calls.ts` stack that Phase 3's 3B social mandate structurally requires and every later phase needs more of.
**Who needs it:** every paid phase (1–6) — flagged independently in all five blueprints as "not phase-specific, but blocks this phase exactly as it blocks the marketplace generally."
**Build cost:** this is the one system on this list that isn't primarily a Convex-schema-and-UI job — it requires a real payment processor decision (see §4, open decisions) before engineering can finish it. Everything else on this list can be built with in-house Convex/UI work; this one has an external dependency.

**Not promoted to a shared system, called out because it's tempting to over-generalize:** group session support (`parties`/`partyGuests` wiring, Phase 2's 2–4 GP groups) and the native-to-native/story-pack content pipeline (Phase 3's Bridge Story packs, Phase 5's recording-collection-with-difficulty-tagging, consumed by Phase 6's un-6 diagnostic) are real cross-phase needs but are **content/product decisions with a thin engineering layer**, not infrastructure in the same sense as 1.1–1.6 — they're sequencing dependencies (§2) and content-investment decisions (§4), not systems to architect up front.

## 2. Recommended build sequence

**0. Finish Phase 1 first — this is not optional preamble, it's a hard dependency.** Three items from `phase1-completion-plan.md` are direct prerequisites for the shared infra above, not just "the previous phase's leftover work":
- **M11 (word-history logging bug)** is the same defect as shared infra item 1.3 above. Fixing it is the first commit of the Phase 2–6 build-out, not a Phase-1-only cleanup — every phase's Word Log feature is built on this data.
- **M12 (wire the placement engine)** matters for the same reason `phase2-blueprint.md` assumes it: Phase 2 entry is gated by `phaseForHours` crossing 100h, and an unplaced experienced speaker forced through the Dirty Dozen wastes the exact hours that should be seeding Phase 2 content.
- **M13 (the 40-meeting spine)** is what makes "Phase 1 hours" mean anything sequenced; without it there's no reliable signal for when a grower is actually ready to promote.
None of Phase 1's content gaps (Lexicarry art, town scenes, etc. — the **Blocked** items) block Phase 2–6 engineering; only M11–M13 do. The five must-have engineering-adjacent items should land before Phase 2 work starts; the content-fidelity backlog (vocabulary suites, Ladder/Sixteen-Pictures mechanics) can run in parallel or trail slightly.

**1. Build shared infra items 1.1, 1.3, 1.4 (thin versions) alongside Phase 2 — not as a separate pre-phase.** This is the order every blueprint's own MVP section already implies: Phase 2's MVP cut (§6) explicitly builds "a bare-bones re-listen player" (1.1, thin), reuses/fixes the word-history store (1.3, already required by M11), and extends `messages.ts` with one new kind (1.4, thin) — it does **not** wait for a fully generalized version of any of the three. Building the thin versions in service of Phase 2, then generalizing as Phase 3–6 add requirements, is cheaper than speccing all three to their eventual full shape before any phase ships. This is also lower-risk: Phase 2 is the one blueprint the fidelity review gave a clean "sound" verdict with zero concerns, so it's the safest place to validate the shared-infra pattern before phases with real open design questions (3, 4, 6) build on top of it.

**2. Phase 2, full build.** Lowest new-infra requirement of any phase 2–6 (per its own §5, the heaviest lift — Listening Library, cue-card fix — is already required by step 1), cleanest AI-legitimacy story (2A's nurturer function is genuinely "mechanical and content-free" per the guide, so Nuri's rehearsal mode isn't a stretch), and the fidelity review's only unqualified "sound" verdict. This is also where item 1.2 (structured multi-take recording) gets its first real implementation as the Clarify Player — building it here, against Phase 2's comparatively simple negotiation shape, is easier than debuting it against Phase 3's massaging or Phase 5's segment-based `clarifyFlow.ts`.

**3. Phase 3, full build — but resolve the 3B→3C gate question (§4) before building the gate at all.** Phase 3 is next because (a) it's the guide's own next phase and nothing in Phases 4–6 is reachable without it per the "continue with your Phase 1/2/3 nurturer" continuity pattern all five blueprints share, (b) it generalizes item 1.2 from Clarify Player into the full Massage Player (segmented replay + the three negotiation moves), which Phase 5 and 6 later reuse verbatim, and (c) it's the one blueprint most focused on *fixing* existing Phase 3 code that's actively wrong (inverted massaging, missing information gap) rather than adding net-new surface — cheap, high-value correctness work. The fidelity review's one open item here (the softened 3B→3C hard gate) should be decided by the owner before the gate ships in any form, soft or hard, since shipping the soft version first and hardening it later is a different engineering path than shipping a real gate from the start.

**4. Phase 4, full build — but design the missing entry/fallback gate before building the Life Story surface.** Phase 4 needs almost the same list of shared infra Phase 3 needed (Listening Library, Word Log, async threads) plus two genuinely new pieces: durable consent/erasure state (not the current session-only `ConsentDialog`) and the HelperProfile generalization (item 1.5) to represent "mentor" as a distinct, untrained role. The fidelity review flags that Phase 4's blueprint has no equivalent of Phase 2's "postpone, extend 2B by 25h" escape hatch despite Phase 4 being the guide's own "sink-or-swim" hardest phase — this should be designed (a literal fallback-to-Phase-3 button, per the guide's own week-or-two-then-retreat rule) before the Life Story Activity ships, not patched in after users hit the wall. Confidentiality/erasure is a floor requirement, not a fast-follow, given what's being recorded — build it with the very first recording surface.

**5. Phase 5, full build — decide the reading-programme placement first.** Phase 5 needs the biggest genuinely-new piece of engineering on this list: `clarifyFlow.ts`, a segment-based sibling to `sessionFlow.ts` (item 1.2's most complex instance). It also needs item 1.5's mentor-quality signal (since Phase 5 mentors are explicitly untrained — `methodCertified` is actively the wrong filter here) and item 1.6's bounty payment shape for recording collection. Before building, resolve the fidelity review's flagged gap: the guide's reading programme starts in Phase 5, not Phase 6, and both blueprints currently place it only in Phase 6 (§4 below) — fix the phase assignment in the spec before building `p5-library`/`p6-read`, since it's cheaper to build in the right phase once than to migrate a shipped feature.

**6. Phase 6, full build — fix the role-play rehearsal bug before building it, not after.** Phase 6 is last because it's the heaviest consumer of every shared-infra item (Listening Library, Massage Player, Word Log, topic-scoped threading, HelperProfile, payments) and because its own helper model — plural, lifestyle-embedded, largely non-marketplace — only makes sense once Phases 2–5 have proven the continuity/matching pattern it extends. One concrete pre-build fix: the fidelity review found the AI role-play rehearsal bridge has the roles backwards (Nuri should play the *customer* so the grower rehearses the professional register the exercise is designed to build, not the other way around) — this is caught at design time now specifically so it isn't caught at QA time after the Discourse-Mastery Pipeline is built.

**Why this order and not, say, "build all shared infra first, then all six phases in parallel":** every blueprint's own MVP section demonstrates that the *thin* version of each shared system is enough to prove a phase's matching/solo/pen-pal thesis, and that generalizing happens naturally as later phases add requirements the earlier thin version didn't anticipate (e.g., topic-scoped threading only becomes necessary once Phase 4 needs per-storyteller threads — building it before any phase needs it risks guessing the wrong shape). Building shared infra to its full generalized spec before any phase ships would mean designing item 1.2 (the multi-take recording primitive) against four different future use cases with no real usage data from any of them — a slower and riskier path than letting Phase 2 prove the shape, then extending it.

## 3. What ships first

**Recommendation: Phase 2, full build (§6 of `phase2-blueprint.md`), built together with the thin versions of shared-infra items 1.1 (Listening Library), 1.3 (Word Log fix), and 1.4 (async thread extension) — not as a separate infra-only release.**

Why this and not a shared-infra-only release, and not a different phase:

- **It is the only blueprint the fidelity review gave a clean "sound" verdict with zero concerns.** Every other candidate phase carries an open design question that should be resolved before building (Phase 3's softened hard gate, Phase 4's missing fallback design and confidentiality floor requirement, Phase 5's reading-programme misplacement, Phase 6's inverted role-play bridge). Phase 2 has none of these — it's the lowest-risk phase to validate the matching/solo-fallback/pen-pal thesis on.
- **It hits all three of the owner's goals with real, not token, mechanisms**, at genuinely low build cost: matching is "continue with your Phase 1 nurturer" (pure UI re-ordering on the existing `requests.ts` — no new backend); solo-fallback is the one Phase 2–6 activity that's *methodologically* legitimate for AI to run essentially unassisted (2A's describe-and-recast, explicitly "mechanical and content-free" per the guide, not a stretched interpretation); pen-pal is the daily "one new fact" card plus voice-note postcards, both near-zero-new-schema extensions of `messages.ts`.
- **A shared-infra-only release has no user-facing proof point.** Building the Listening Library or the Word Log in the abstract, with no phase consuming them yet, risks over- or under-building their shape (see §2's reasoning against building all infra first). Phase 2's MVP already scopes the *right-sized* thin versions of both — building "Phase 2" and "the infra Phase 2 needs" are the same piece of work, not two.
- **It's cumulative leverage, not a detour.** Every later phase reuses what Phase 2 builds: the Clarify Player becomes the Massage Player (Phase 3) becomes `clarifyFlow.ts` (Phase 5); the thin Listening Library becomes the shrinking-copy version (Phase 5) and the topic-scoped version (Phase 4/6); the messages.ts voice-kind extension becomes the Idea Board and Epic thread (Phase 3) and journal/topic-nudge attachments (Phase 4).

If the owner's priority is instead "prove the hardest, highest-stakes case works before investing further" (i.e., de-risk Phase 4's confidentiality model or Phase 5's native-to-native sourcing problem specifically, since those are the two places a mistake is costliest), that would argue for building Phase 4's confidentiality/erasure layer or Phase 5's recording-sourcing pipeline as an early spike — but neither is a full phase v1, and both depend on infra (Listening Library, Word Log) that doesn't exist without Phase 2 or an infra-only sprint first. Phase 2 remains the recommended v1 under either framing; a Phase 4/5 spike would be additive, not a substitute.

## 4. Open decisions for the owner

These cannot be resolved by engineering or content work alone — each is flagged by a blueprint or the fidelity review as needing an explicit owner call before (or instead of) building.

1. **Lexicarry bubble-strip artwork (B-1, Phase 1, blocks M14).** Neither the homemade packet nor the commercial Lexicarry book's art can ship (copyright). Decide: commission original illustration (budget/timeline), scope a carefully-bounded AI-generation pipeline for genuinely original art, or explicitly cut Cartoon Bubbles down to a smaller function subset for launch.
2. **Town/Landscape scene art and world-map/countries art (B-2, B-3, Phase 1).** Same copyright constraint, same three-way decision (commission / AI-generate / scope down), plus a **localization target** call for the Town Scene redraw (the guide's own version is post-Soviet Central Asia — does Nuri's version stay generic, or localize per learner cohort?).
3. **Form-focused/structured-input grammar games (B-4, Phase 1, feeds Phase 3's S18).** Not a copyright issue — an ongoing content-ops cost issue. The guide's own version is built "with a linguistic consultant, per host language." Decide: invest in per-language grammar-game templates (large, ongoing cost), ship a best-effort generic template, or cut from scope.
4. **Courses-lock vs. practice-hub inconsistency (N11, Phase 1).** `/courses/*` hard-locks everything past Phase 1; `/practice/*` games stay reachable at any phase via direct URL. Likely intentional (phase-agnostic maintenance drills) but currently undocumented as a decision — needs an explicit yes/no so it isn't accidentally "fixed" into a worse state later.
5. **The Phase 3B→3C hard gate.** The guide says "HARD GATE" in so many words; the blueprint ships it soft (a checklist item, not a block) with no stated path back to hardening it. Decide whether the app should ever actually block progression on this self-reported social-hours metric, or whether "soft, permanently" is the intended product stance — and if soft, whether that should be stated as a deliberate methodology deviation rather than an implementation detail.
6. **`NEXT_PUBLIC_ENABLE_COMMUNITY_EXCHANGE` rollout.** Currently default-off. Phase 3's 3B social mandate has no path to satisfaction without turning this on (at least for Phase-3+ profiles); Phases 4–6 need it more, not less. Turning on 1:1 messaging/calls/requests between growers and non-vetted host contacts is a real trust-and-safety surface, not just a feature flag — needs an explicit go/no-go and, if go, a moderation/reporting plan the current blueprints don't specify.
7. **Real payment processor integration for `credits.ts`.** Every phase from 2 onward is blocked on `recordEntry` actually recording verified session/payment events, and Phase 5 additionally needs a new per-deliverable bounty payment shape. This is a real "pick a processor, handle payouts to nurturers/mentors across PPP-scaled international rates" decision, not an internal engineering task — needs owner sign-off on the business/compliance side before it can be built.
8. **Reading-programme phase placement (Phase 5 vs. Phase 6).** The source guide starts extensive reading in Phase 5; both blueprints currently place it only in Phase 6 (`p6-read`), inheriting a known app-vs-guide delta rather than fixing it. Decide whether to correct the phase assignment (cheap now, since neither phase's reading feature is built yet) or deliberately keep it at Phase 6 for product reasons (e.g., simpler to introduce reading after the native-to-native listening skills Phase 5 builds).
9. **Monetization/business model of the matching layer generally.** None of the five blueprints propose take-rate, subscription, or margin structure on the nurturer/mentor marketplace — they design the matching *mechanics* (continuity defaults, attribute search, certification tiers) but not the *business* of it. Worth an explicit decision before Phase 2's "continue with your nurturer" flow and Phase 5/6's bounty payments go live, since retrofitting monetization onto an already-live marketplace is harder than designing it in.
10. **Group session pricing (2–4 GPs per nurturer, Phase 2's `parties`/`partyGuests` wiring).** The guide treats groups as a real methodological preference, not just a scheduling convenience — but neither the existing schema nor any blueprint specifies how `ratePerHourUsd` should split or scale across a 2–4-person group session. Needs a pricing decision before group sessions ship, not after.
11. **Content-authoring investment for AI solo-mode "story packs" (Phase 3) and per-language coverage generally.** Phase 3's Bridge Story AI fallback needs hand-authored `{sentences[], perWordGlossary[]}` packs per language; Phase 1's audio pipeline already only fully covers 3 of 10 "full-content" languages. Decide how many of the 19 supported languages get first-class AI-fallback content at launch vs. a smaller flagship set (the blueprints default to "start with Cinderella/ru," which is a reasonable MVP call but an explicit scope decision, not a given).
12. **Whether to accept the fidelity review's "AI substitutes for X" framing across the board, or tighten it further in specific spots.** The overall stance (AI never fabricates biography, cultural interpretation, or native-to-native speech; always labels rehearsal vs. real) is sound and consistent — but two spots deserve an explicit owner nod given they're closer calls: Phase 2's Bridge-Story-style reasoning applied to a whole ~half of Phase 3's session time running on AI narration (fidelity review's Phase 3 item 2 — technically fine, but worth confirming the owner is comfortable with AI carrying that much raw session-time even where it's honest), and Phase 4's un-flagged retelling-anonymization gap (a real person's confidential life story could get retold into the pen-pal thread without a structural reminder to anonymize it — worth deciding whether that needs a hard UI guard, not just a documented norm).
