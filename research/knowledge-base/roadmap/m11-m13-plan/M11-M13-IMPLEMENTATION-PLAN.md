## 3. Per-item summary (work-ticket descriptions)

**M11 (word-id logging fix + word-history panel).** The live session room (`session/page.tsx`) currently logs a numeric review-correctness score instead of the actual card ids introduced during the session, so `profile.wordIds` — the exact "which words has this grower met" ground truth the app needs for cue-card/word-history features — has been silently uncounted for every live Dirty Dozen session since launch. The fix is a same-file, ~3-line call-site change (pass `flow.deck.slice(0, flow.introduced).map(c => c.id)` instead of `points` to `completeActivity`), using a pattern that already works correctly in `practice/vocabulary/page.tsx`. Ship this piece (M11a) immediately and standalone — no schema change, no risk to `sessionFlow.ts`. Once landed, extend the existing `CardTable` component in the Nurturer Studio (M11b) into a per-grower "words so far" panel: cross-reference `profile.wordIds` against the domain's `VocabItem[]`, add a met/highlighted state and a derived sequential number (array index + 1 — no new field needed since `Set` insertion order is already stable), and a running count. Done looks like: (1) after a live session ends, `profile.wordIds` grows by exactly the number of cards introduced that session, verifiable by comparing session-end `flow.introduced` count to the delta in `wordIds.length`; (2) the Nurturer Studio shows a real, non-empty, per-grower word list with correct sequential numbering for any profile that has completed at least one live session or vocabulary-practice session.

**M12 (placement engine wiring).** `src/lib/placement.ts` is a complete, self-contained 232-line comprehension placement engine (two gates, 85% pass bar, TPR chains) that has zero importers anywhere in the app — every new profile is hardcoded to `phase: 1` regardless of prior fluency. This ticket wires it into onboarding as an optional, skippable branch shown right after target-language selection (step 2): a dismissible card offering "test out?", opening a full-screen `PlacementCheck` overlay (new component) that runs Gate 1 (and, on pass, offers Gate 2), and on completion stores the earned phase in local onboarding state until `finish()` applies `placementSeed(placedPhase)` to the assembled `Profile`. No engine or schema changes are required — this is pure UI wiring against existing exports. Because a placed Phase-2/3 grower lands on a currently-locked `/courses/[slug]` preview page (a pre-existing gap, not introduced by this ticket), the result screen must be explicit about what a grower gets today (practice games in review/maintenance mode, nurturer-booked sessions) rather than silently placing them somewhere sparse. Done looks like: a returning/fluent test user can go through onboarding, choose a target language, opt into the placement check, pass Gate 1 and/or Gate 2, and land on `/dashboard` with `profile.phase`, `hoursLogged`, and `wordsMet` correctly pre-seeded (verifiable in the stored profile object) — while a user who skips or fails sees zero behavior change from today.

**M13 stopgap (meeting-spine sequencing fix).** Of the app's 40 "meetings," only 17 meeting numbers actually have fresh vocabulary assigned (verified directly against `vocab.ts`'s 237 items / 28 domains) — the other 23 serve a 100%-review deck with zero new content, because `meetingForHours` is a flat `hours/2` proxy with no awareness of which numbers are populated. Separately, the Nurturer Studio's Session Planner has zero grower-specific gating and can hand a 0-hour beginner a 1B activity (e.g. Marketplace Role-Play) in the same draw as Dirty Dozen. Both are fixed additively with no new content authoring: (1a) `meetingForHours` gains a snap-down table (`POPULATED_MEETINGS`) so it only ever returns one of the 17 real meeting numbers — callers (`buildMeetingDeck` and its call sites) need zero changes; (1b) `SessionPlanner`'s `buildPlan` gains a `part1a` flag that filters `phase.activities` against `phase.parts["1a"].activityIds`, reusing the exact filtering pattern already proven in `session/page.tsx:192-197`, plus a small UI toggle defaulting to 1A. Done looks like: (1) a grower's `meetingForHours(hoursLogged)` output, across the full 0–80+ hour range, only ever returns a value from `{1,2,3,4,5,7,8,9,11,12,14,18,19,25,32,33,37}`, verifiable by sweeping `hoursLogged` through that range and confirming no returned meeting produces a zero-fresh-card deck; (2) a nurturer planning a session for a beginner with the 1A toggle on never sees a 1B-only activity (e.g. `p1-market`, `p1-power`) in the generated plan.

## 4. M13's full-fidelity slice — explicitly deferred (NOT part of this build)

This is L-effort content authoring plus one data-model addition, carried forward from M13's own plan for visibility — it is **not scheduled** in the build order above and should not start until the owner confirms content-authoring bandwidth.

**4a. Content authoring for the 23 unpopulated meetings.** Each empty meeting number needs real vocabulary/activity content matched to the guide's own meeting-by-meeting map (fully cataloged in `phase1.md`). Critically, **this is not separate labor from several already-tracked roadmap items** — M1 (checkpoints), M3 (Grand Refreshing), M4 (Physical States/Needs), M5 (possessives), M6 (time/calendar suite), M7 (MP38-40 capstone), M8 (numbers-beyond-10), B4 (question-words), B9 (world-map), B10 (town/landscape), B11 (if/then sequencing) collectively *are* the content that fills these 23 gaps, just organized by activity-type instead of meeting-number. Recommend tracking as one coordinated content backlog rather than duplicating effort under a separate M13 heading.

**4b. New `MeetingPlan` data model (additive).** A new optional type + `MEETING_PLANS: MeetingPlan[]` table (new file `src/lib/meetingPlans.ts`) digitizing the guide's 40-row meeting index: `{ meeting, part, theme, vocabDomainIds, activityIds, grammarFocus?, notes? }`. Does not touch existing `VocabItem`/`VocabDomain`/`Phase` shapes, so nothing that reads them today breaks. `sessionFlow.ts` continues working unchanged; `MEETING_PLANS` is metadata the Nurturer Studio / course pages can optionally consult later for richer per-meeting UI once the content backlog (4a) is substantially filled in.

**4c. Timer/Planner realism (session-shape rework).** The Meeting Timer is hardcoded to a fixed 3-segment, 30-minute shape; the Planner caps at 60 minutes / 4 activities, vs. the guide's real 2-3 hour, 4-8-game 1B meetings. Fixing this requires both a data-shape unification (make the Timer consume the same `PlanBlock[]` the Planner already produces, instead of maintaining a second disconnected segment model) and non-trivial UI rework (variable segment count, variable boundary cues instead of the current fixed `b1`/`b2` two-boundary logic). M13's own plan recommends this be tracked as its own L-effort item, cross-referenced from M13 rather than merged into it.

**4d. Persisted "meeting attended" flag — DECIDED 2026-07-20, not yet built.** Owner's ruling: solo `/practice/*` grinding must NOT advance "meeting N of 40." Reasoning (owner's words, condensed): the app exists to get people actually communicating with real people — that's the only way to learn a language — so meeting-number progression must require a genuine live, nurturer-led session; solo practice is fine and expected at the initial beginner stage (and keeps early sessions from being tedious for nurturers), but shouldn't be a way to fast-forward the curriculum alone. Solo practice should keep building vocabulary/hours/points as it does today — it just shouldn't move the meeting-number needle.
**Not yet resolved:** whether "live, nurturer-led session" means specifically a real human nurturer, or any structured live `/session` room play including the AI nurturer Nuri — material because human marketplace matching is demo data today ("beta always gets the AI" per `nurturer-side.md`), so a human-only reading would freeze meeting progression for nearly every current user. Needs one more owner call before this is built. Still correctly out of scope for the immediate M11a/M13-stopgap/M12/M11b build (steps 1-5) — this is schema + policy work for the deferred full-fidelity slice, not a blocker to what ships now.

## 5. Open questions for the owner

1. **Random-draw sentence generator (guide's B2c mechanic, e.g. "draw location + 2 objects → make a sentence").** M11's plan defers this because it needs a domain-role taxonomy (which domains act as "locations" vs. "objects" vs. "kin" vs. "actions") that doesn't exist in `vocab.ts` yet, and argues it more naturally belongs under M3 (Grand Refreshing), the guide's actual consumer of the mechanic. Decision needed: formally re-home it under M3 in the roadmap doc, or keep it nominally under M11 with an explicit "blocked on taxonomy" note?
2. **Per-word timestamp / "first met" tracking.** Currently `wordIds` only answers "has this word ever been met" (yes/no), not "when," so the guide's coverage-reminder ("avoid favoritism/ruts") can't be reconstructed after the fact. A follow-up field (`ActivityAttempt.wordIdsAdded?: string[]` or `Profile.wordMeta?: Record<string, {firstMetAt, meetingIntroduced}>`) would unlock it later. Decision needed: file this as its own tracked future ticket now, or leave unticketed until a concrete feature needs it?
3. **Word-history panel audience.** M11b's plan puts the "words so far" panel in the Nurturer Studio, gated the same way the rest of that page already is (nurturer/training role gates). Decision needed: is a grower-facing version of the same list (e.g. on `/dashboard`) wanted as a companion surface, or nurturer-only for now?
4. **Placement-seeded profiles have `wordsMet` set but `wordIds: []`.** `placementSeed()` seeds a count (e.g. 1,000 words) but no actual word ids, so a placed Phase-2 grower's word-history panel (M11b) would show an empty list despite the profile claiming real vocabulary. This mismatch already exists today for anyone reaching Phase 2 by hours alone, so M12 doesn't introduce a new bug — but decision needed: ship with a code comment acknowledging the gap (recommended, no code change), or invest in reconciling it now?
5. **Permanent "placed via test-out" record.** No field currently distinguishes a profile that reached Phase 2/3 via placement vs. organic hours. Decision needed: add an optional `placedAt?`/`placementResult?` field to `Profile` now (for a future "you tested into Phase 2" badge/receipt), or skip until product actually asks for that UI?
6. **Session Planner's 1A/1B toggle has no grower-specific default.** The stopgap (M13 1b) adds a manual 1A/1B toggle because the Planner has no "which grower is this for" selector to auto-default from `hoursLogged`. Decision needed: is a grower-picker (enabling an automatic 1A/1B default, mirroring `session/page.tsx`'s own behavior) a near-term follow-on, or does the manual toggle stay the permanent UX?
7. **DECIDED 2026-07-20 — Solo `/practice/*` hours must NOT advance "meeting N of 40"; only a live, nurturer-led session should.** See §4d for full reasoning and the one still-open sub-question (human nurturer specifically, vs. any live `/session` room play including AI-guided Nuri sessions).
8. **Should M11a (logging fix) and M11b (word-history panel) ship as one PR or two?** The roadmap lists M11 as a single line item, but the two pieces differ sharply in size and urgency (a ~3-line data-integrity fix vs. a new UI panel). This synthesis recommends splitting into two PRs (M11a immediately, M11b once M11a is live) — flagging for explicit owner sign-off since it changes how the roadmap item is tracked/closed.
